# 跑测试、选参数、读结果

## 1. 角色与拓扑：必须先问清楚

`--role` / `--topology` 决定**被测设备在配对里扮演什么**，进而决定 WiFi 相关
测试怎么跑。填错不会报参数错误，只会一堆超时 —— 而超时看起来像设备坏了。

| 组合 | 开热点 | 连路由 | 说明 |
|---|---|---|---|
| `--role rx --topology 1to1` | 是 | 是 | Tx 连它；它连路由 |
| `--role tx --topology 1tomany` | 是 | 是 | 多个 Rx 连它；它连路由 |
| `--role tx --topology 1to1` | 否 | 否 | 只连 Rx 的热点 |
| `--role rx --topology 1tomany` | 否 | 否 | 只连 Tx 的热点 |

关键规则：**开热点的那一方同时也是 station**，负责连路由，给自己和对端提供
上网 / OTA。所以"是不是 AP"和"要不要连路由"是同一个判断
（代码里 `Setup.is_ap` / `Setup.is_sta`）。

**拓扑会翻转角色的身份**：同一台 Tx，一对一时是客户端、一对多时是热点。
所以只问 Tx/Rx 不够，必须连拓扑一起问。

推论：扫描路由 / 连接路由 / 忘记网络这几条**只有连路由的那一方做得到**。
对一台一对一的 Tx 跑这些，结果是全部超时。工具会按角色先筛一遍，把不适用的
直接排除掉 —— 所以 `-s` / `-w` 的必要性也跟着角色变。

## 2. tag 的安全分级

| 级别 | tag | 说明 |
|---|---|---|
| 安全 | `query` | **只读查询**，随便跑，不需要 `-s`/`-w` |
| 安全 | `display` `audio` `encode` `net` `wifi` `log` `cast` `ota` `tx` `sys` | 改运行时状态，不持久化 |
| 默认 | `core` | WiFi 老化主流程（扫描→取结果→连接→忘记→切 5G） |
| 需配对 | `remote` | 由**对端** AM 执行，没配对就是全超时 |
| **危险** | `danger` | 改 SSID/密码、OTA 升级、恢复出厂、重启 |
| **致命** | `logmode` | 开 log 后设备不再回应任何 UART 命令，救不回来 |

`danger` / `logmode` 不带任何其它 tag，只有显式指定才会跑到。
`logmode` 也**没有进基线恢复** —— 否则每轮收尾都会把命令通道弄死。

更细的子类：`rotate` `zoom` `hdmi` `hdcp` `role` `region` `band` `pair` `ap`。

**每组有几条测试以 `--list-tests` 的输出为准**，不要从文档抄数字。

## 3. 循环与重试

```bash
-c 1        # 功能验证
-c 500      # 老化测试
-r 3        # 单轮失败最多重试 3 次；重试前自动清缓冲 + 忘记网络
```

`-c` 作用在**整个测试集**外层，和 `--tags` 正交 —— 任何 tag 组合都能循环跑。

**`-c` 默认是 100。** 做功能验证一定要显式 `-c 1`，否则会跑很久。

## 4. 超时预算

| 位置 | 超时 | 理由 |
|---|---|---|
| 每步第一个包 | `-t`，默认 30s | 判断设备是否还活着 |
| 包内字节间隔 | 1s | 115200 下 1024 字节只需 90ms |
| 网络名确认包 | 15s | 实测连接应答 5.2s，留 3 倍余量 |
| 断开通知包 | 5s | 实测 0.5s 内到 |
| 启动/重试前清理 | 5s | 可能本来就没连网络，不该干等 |

设备慢时放宽 `-t`，但**先怀疑角色填错**（那是超时的头号原因），再怀疑设备慢。

另有 `max_duration` 是**单条测试的时延上限**，超了算失败。老化测试里性能退化
是真实的失效模式：返回码都对，但连接从 5 秒变成 25 秒 —— 只看通过/失败发现不了。

## 5. 报告

```bash
--report-json run.json     # 机器可读，老化测试看这个
--report-junit run.xml     # CI 直接展示
```

日志（`-l`）是给人看的，报告是给机器看的，只用标准库生成。
**Ctrl+C 中断也会写报告** —— 长跑靠 Ctrl+C 结束是常规操作。

JSON 里每条测试有 `pass` / `fail` / `skip` / `pass_rate`，以及 `meta` 里记的
`role` / `topology`。老化测试最该看的两个数：

- **偶发失败率**（`pass_rate`）—— 500 轮里挂 2 次这种，单轮跑不出来。
- **时延退化趋势**——比 `max_duration` 的硬上限更敏感。

## 6. 失败了先查什么

| 症状 | 先查 |
|---|---|
| 全部超时 | **角色/拓扑填错**（头号原因）；其次串口号、波特率、设备没上电 |
| **程序卡死、一行输出都没有** | macOS 上用了 `/dev/tty.*` —— 打开时会阻塞等 DCD。换成 `/dev/cu.*` |
| 端口根本打不开 / 找不到 | 先跑 `python3 -m serial.tools.list_ports -v`。列不出来是驱动问题（CH340/CP210x/FTDI），不是代码问题 |
| Linux 上打开被拒（权限） | 用户不在 `dialout` 组，或加了组没重新登录 |
| `remote` 组全超时 | 没和对端配对 |
| 连接网络失败 | `-s`/`-w` 有没有给；SSID 是不是 5G-only 而设备当前在 2.4G |
| 设备不再回应任何命令 | 是不是跑过 `logmode`。只能物理重启 |
| 偶发失败 | 加 `-c 500 -r 3 --report-json`，用 `pass_rate` 定性，别靠单轮结论 |
| 改完代码不确定有没有写错 | `python3 -m unittest discover`（不接设备） |

排查时可以加 `--no-restore` 让设备停在被改过的状态，方便看现场。

## 7. 手动调协议

`-i` / `--interactive` 进指令模式：从指令表选，或手输十六进制，单条发送看应答。
**这是给人用的菜单，agent 不要调用**（会等输入）。

指令列表里 `!!` 开头的会改持久配置或让设备失联（包括开 log 的三条）；
`[PL]` 后缀是 Remote 指令，由对端执行，没配对就是超时。
